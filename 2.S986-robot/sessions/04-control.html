Module 4 — Closed-loop control and tuning

Summary

The objective of this module is to spin the motor for the first time, understand the parameters at play and optimize gains. The Seeeduino, ESC and encoder are wired already and we will seek to command the ESC via the Seeeduino, running continuously, then holding position, then tracking a velocity setpoint with a tuned loop.

Requirements

Parts Motor with new shaft from Module 2, ESC from Module 3, Seeeduino XIAO nRF52840
Tools Bench supply with current limit, camera, soldering iron
Read This page in full - the speed limits below explain most of what comes up

Electronics check

Check the state of the electrical connections to the encoder and to the flight controller. Have someone else verify the connections. Watch out for swapped wires, weak/cold solder connections and check the R14 connection point.

WarningProblems

Most problems with SimpleFOC come from badly soldered cables and miswiring.

Firmware

The ESC needs to be flashed with SimpleFOC. A custom version of the code for the B-G431B-ESC1 motor controller, using the SimpleFOC library, is to be found here: FAAV-G431-ESC. See Software for all repositories.

Before changing anything in there, read How SimpleFOC works. It covers the two nested loops, what the FOC maths does each iteration, why the motor twitches at power-on, and which settings in the sketch matter - enough to read the firmware rather than guess at it.

Controlling the motor from a laptop

Next, install SimpleFOC Studio: SimpleFOCStudio. It is a desktop GUI that drives the same commander interface described below, so instead of typing commands into a serial monitor you get a form for every motor parameter, live plots of the monitored variables, and a button that dumps the tuned values back out as Arduino code.

Laptops can block the connection to the Seeeduino (over USB-C) if the Seeeduino is powered over 5V through the pin. If that happens, power needs to be disconnected. Two options are possible: either a UBS-C power isolation module or disconnecting the 5V line between ESC and Seeeduino.

WarningTorque control mode

Do not change the torque control mode in the GUI. It will display voltage mode but the ESC actually runs a newer estimated control mode.

Figure 1 shows the parts you will actually use: the parameter tree on the left, the live plot of target, velocity and angle in the middle, and a command line at the bottom for anything the form does not expose.

NoteWhat the ESC code has to provide

Studio does not work against arbitrary firmware. The ESC code must register the motor with the commander (command.add('M', doMotor, "motor")), enable monitoring with motor.useMonitoring(Serial), and call both motor.monitor() and command.run() every loop. The command letter set in Studio’s device settings has to match the one in the sketch - M in our case.
On this robot the ESC’s own micro-USB serial is gone - those pins were repurposed for the encoder’s SPI3 bus in Module 3 - so the port Studio opens is the Seeeduino’s USB serial, and the Seeeduino has to pass what it receives through to the ESC on Serial1 (essentially it needs to act as a relay). Studio cannot reach the ESC on its own.

Commanding and monitoring the ESC

This is a high-level summary of the SimpleFOC communication docs. The ESC is driven through the commander, a practical interface for setting and getting values (instructions). Ask the commander for available commands with ?. Commands available:

Command Effect
M Full motor configuration
F Get the main loop frequency
L Turn the onboard LED on and off (useful as a comms check)
T Set the target value - rad, rad/s or N/m depending on control mode
S Get current angle and velocity
W Watchdog on/off. If no new target arrives for 1 s, target is set to zero. On by default
ME Enable the driver. ME1 energises the phases, ME0 switches them off and the motor coasts
MC Motion control type. MC0 torque, MC1 velocity, MC2 angle
MLC Current limit, in amps

The M prefix is the motor command, and the letters after it walk down into its settings - MC is the motor’s control type, MLC the motor’s limit on current. That is why full configuration is just M on its own.

When it comes to commanding from the flight controlling direction, your code shouldn’t write these directly. Instead, you should create wrapper functions such as “current_limit(value)” etc…

WarningCareful when changing control mode

T means something different in each mode, position, velocity, or torque. Sending a velocity setpoint while in torque mode will do something unintended. BE VERY CAREFUL ABOUT THIS.

Tasks to do:

  1. Change the motor command letter (towards the bottom in the interface) to M.
  2. Commander responds to ? over serial from a laptop, L toggles the onboard LED.
  3. The sensor returns a plausible angle through a full manual rotation.

Tuning the cascaded controller

Figure 2 is the structure SimpleFOC implements. We need to tune it.

Each stage turns its own error into a setpoint for the stage inside it. That is the whole idea, and it is why the two clamps in the middle are not decoration: the velocity limit caps what the angle loop is allowed to ask for, and the current limit caps what the velocity loop is allowed to ask for.

Tune from the inside out. Work in this order, and do not move outwards until the loop you are on behaves:

  1. Torque first, in torque mode (MC0). Command a current and check the motor takes it smoothly, without whine or oscillation.
  2. Velocity next (MC1), once torque is solid. Proportional gain first, then integral. Watch the low-pass filter on the velocity feedback while you do: heavy filtering looks like it is cleaning up noise, but the lag it adds is what makes the loop hunt.
  3. Angle last (MC2). Usually proportional gain alone is enough, because the velocity loop underneath is already doing the work.

The order is not a convention, it is a dependency. An outer loop tuned against a sloppy inner loop is partly compensating for the inner loop’s error, so its gains encode that error - and they stop being valid the moment you go back and fix the inner loop.

These four PID blocks are exactly what SimpleFOC Studio exposes in its parameter tree (Figure 1). That is the practical argument for having installed it: you can change a gain and watch the step response without reflashing between attempts.

SimpleFOC documents each stage separately: torque control, the velocity loop, the angle loop, and cascaded position control for the structure in Figure 2 as a whole. The exact forms being tuned are in the PID implementation and the low-pass filter.

Record how it responds to a step change:

Do these in Studio. For each one, capture the step response and write down the gains that produced it. A screenshot without its gains is not a result: nobody can reproduce it.

Two things to set before the first capture.

  • Turn the watchdog off for the duration (W0). It is on by default and zeroes the target after 1 s without a new one, so it will pull your step back down in the middle of the capture and look like a controller fault.
  • Plot the variable the loop actually controls - current in torque mode, velocity in velocity mode, angle in position mode - and leave Target enabled in all three so the step is visible.

  1. Torque mode (MC0). Set the velocity limit to 200 rad/s, then block the output with your hand or a piece of tape before commanding any current - in torque mode nothing limits speed, so an unblocked motor just accelerates until friction stops it. Set the current limit with MLC, starting around 1 A, and step the target.

  2. Velocity mode (MC1). Step from standstill to 400 rad/s and capture the response. Note that this is motor speed, not the flapping frequency of the final system. Mount a small flag (piece of tape) on the output so rotation is visible and countable.

  3. Position mode (MC2). Step from 0 to 144 rad and back to 0 - about a full flap cycle after reduction - and capture the response.

Report rise time, overshoot and any steady-state error read off the plot.

WarningA blocked motor turns every amp into heat

With the output held there is no back-EMF and no mechanical work, so all the electrical power goes into the windings. Apply the torque step in bursts of a few seconds and let the motor cool between attempts if needed.

Calibration

We’d like to also make sure that we have the right motor parameters for running at high speeds (above 400 rad/s). To this, we will follow the commissioning instrutions in the firmware above. Do this with your TA. Run autocal until 1000 rad/s.

Why we use an ESC that we reprogram

Why low speed is the hard part

Regular drone ESCs start losing synchronisation at low speed, which is exactly the regime used for water propulsion. That is the reason this course uses an FOC ESC rather than a hobby unit - see Design notes.

Why high speed is the hard part (going beyond 600 rad/s)

Two issues limit speed: the micro-controller loop rate, and delays from the rotation sensor. Using SPI at 10 MHz and an AS5047P sensor rated for 28kRPM speeds are the required hardware changes that improves on delay. But at very high speeds, sensor lag still becomes the binding constraint, and shows up as high current draw and noise. We need to update the sensor electrical angle offset as a function of speed. Compensating sensor lag as speed increases is necessary to go above 600 rad/s without wasting current. This is automated by ramping through the speeds and minimising phase current. This SimpleFOC forum thread is useful on the topic.

NoteCheckpoint

Continuous rotation at 1 Hz, position hold against a hand disturbance, and a recorded loop frequency from F. The robot should be tuned, operating in various modes and can be commanded from the flight controller
